## Findings

### DL2-P5-1 — Historical inline profile secrets survive inside preset collections

- Severity: high / Confidence: certain
- Evidence: Before the credential store, saving a legacy bot preset copied all durable profiles, including then-supported inline `providerOptions.apiKey` and Vertex service-account fields (`28eb3fb66:src/ts/storage/database.svelte.ts:4940-4969`; `28eb3fb66:src/ts/model/modelProfileRecords.ts:31-67`). The current repair is explicitly restricted to `settings.modelProfiles`: `if (!isRecord(settings) || !Array.isArray(settings.modelProfiles)) return false` (`server/fastify/src/repository.ts:265-292`), while collection rows are parsed and returned without repair (`server/fastify/src/repository.ts:1448-1462,1520-1525`). The exhaustive mask registry now covers only top-level legacy preset keys and `providerCredentials`, not `botPresets[*].modelProfiles[*]` or `modelPresets[*].modelProfiles[*]` (`src/ts/providerSecretMask.ts:12-55`), yet the authenticated legacy-preset route relies on that registry before returning the complete row (`server/fastify/src/routes/resourceReads.ts:619-637`). Extraction can copy the untouched `modelProfiles` field into `model_presets` (`server/fastify/src/commands/splitPresets.ts:190-223`; `src/ts/presetSplit.ts:3-18,215-223`). The bug-report exporter keeps `modelPresets`, applies the same incomplete registry, then downloads and copies the JSON (`src/lib/Setting/Pages/Advanced/SettingsExportButtons.svelte:15-21,23-67,75-80`).
- Loss scenario: A pre-credential-store user saves a legacy preset while a profile contains an inline API key/private key → after upgrade, settings load scrubs only the top-level profile but the `bot_presets` row retains its copy → opening that preset returns the raw secret to the browser; extracting it places the same secret in `model_presets` → “Export Settings for Bug Report” writes it to a shareable file and clipboard, durably losing credential confidentiality and enabling account/key abuse.
- Fix direction: Repair nested `modelProfiles` in both `bot_presets` and `model_presets` transactionally before any read or command baseline, and retain nested mask paths as defense in depth. Add regression coverage for pre-store rows through legacy hydration, extraction, aggregate collection reads, and bug-report export.

### DL2-P5-2 — Count retention does not bound request-history bytes

- Severity: high / Confidence: certain
- Evidence: The schema accepts unrestricted `TEXT` for `prompt_json`, `response_text`, metadata, and errors (`server/fastify/src/requestHistory.ts:86-105`). `beginRequestHistory` persists `JSON.stringify(input.prompt)` intact (`server/fastify/src/requestHistory.ts:135-160`); streaming appends every token to one string and `completeRequestHistory` writes the entire result without truncation (`server/fastify/src/requestHistory.ts:174-268`). Pruning considers only the newest row count (`server/fastify/src/requestHistory.ts:272-304`), whose allowed maximum is 10,000 (`server/fastify/src/requestHistory.ts:6-7`; `server/fastify/src/routes/commands.ts:9357-9360`). The Ollama tool proxy likewise appends every chunk and stores the completed body (`server/fastify/src/ollamaCloudToolProxy.ts:169-179,300-324`), while its refreshed deadline permits a continuously producing stream to remain open (`server/fastify/src/requestAbort.ts:37-51`).
- Loss scenario: A user retains request history and repeatedly sends large prompts or uses an upstream that produces very large/long streams → each full prompt and response is committed while the row count remains below the configured limit → `risu.db`/WAL consumes the remaining volume → subsequent chat/settings SQLite commits fail; streamed or optimistic user work that could not commit is lost on reload, and all durable state becomes unavailable until storage is recovered.
- Fix direction: Enforce per-field/per-record byte limits while collecting prompts, responses, metadata, and errors, and prune by a total byte budget as well as row count. Prefer truncating this diagnostic artifact (with explicit truncation metadata) before it can exhaust the primary database volume.
