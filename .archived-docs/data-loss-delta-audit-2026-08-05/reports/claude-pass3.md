## Findings

### DL2-P3-1 — Export-then-reset silently exports a pointer stub for legacy cold-storage chats

- Severity: medium / Confidence: probable
- Evidence: `src/ts/characters.ts:1049-1060` — `exportAllChats` serializes `char.chats` as-is after hydration; for a cold-storaged chat the durable server rows themselves ARE the stub (`chat.message` = one message whose `data` is `coldStorageHeader + key`, see `src/ts/process/coldstorage.svelte.ts:218-224` and the server-side pointer validation at `server/fastify/src/routes/commands.ts:6133-6136`), so strict hydration succeeds and the exported JSON contains the pointer, not the conversation. The reset then deletes the live chat/message/hypa rows (`routes/commands.ts:6018-6022`). The real messages survive only in server legacy storage `coldstorage/<key>` (`routes/commands.ts:996`, `readLegacyStorageValue`), now referenced by nothing in the database (`listColdDataKeys`, `coldstorage.svelte.ts:79-96`, walks live chats only). Cold-storage *creation* and *GC* are disabled in this fork (`makeColdData`/`removeColdStorageItems` are no-ops, `coldstorage.svelte.ts:71-77, 233-235`) but recovery commands exist on both character and chat (`routes/commands.ts:5650, 6109`), i.e. legacy stub chats are a recognized server-DB state (upstream-RisuAI migrations).
- Loss scenario: a user who migrated from upstream RisuAI with cold-storaged chats runs "export all chats then reset"; the export "succeeds" and the double-confirmed reset wipes the chats. The exported JSON — the artifact the flow presents as the durable backup — contains a one-line pointer stub instead of the conversation. On the same install the data is recoverable (re-import recreates the stub; opening triggers `preLoadChat` recovery, and the `save/` dir with `coldstorage/` keys is inside the backup contract, `repository.ts:2674`). But if the user relies on the JSON alone — fresh install, wiped server data, sharing the file — the chat's entire message history is silently gone: import restores a stub whose key resolves to nothing, and recovery fails.
- Unverified link: whether the fork's legacy import paths actually carry upstream `coldstorage/*` storage keys together with stub chats (the presence of both recover commands and server-side key reads strongly implies yes, but I did not trace an upstream-save import end-to-end).
- Fix direction: `exportAllChats` should detect `coldStorageHeader` pointers and either inline-resolve them (fetch the cold item and serialize the real messages) or fail the export loudly, mirroring `risusave_incomplete_blocks` — never gate a destructive reset on a pointer-only export.

## Free-hunt findings

### DL2-P3-F1 — Messages appended between export completion and reset settlement are destroyed and absent from the export

- Severity: medium / Confidence: probable
- Evidence: `src/lib/SideBars/SideChatList.svelte:1002-1030` — after `exportAllChats` resolves, the user sits in two `alertConfirm` dialogs (unbounded dwell time); the only guard before the reset is `hasConflictingStructureMutation([chatOrderConflictKey(characterId)])`, which covers client-local *structural* chat mutations only — message appends (server-side generation done-frame writes, second-device/second-tab sends) do not register there. At dispatch, `executeServerCommand` reads the *current* revision (`src/ts/server/commands.ts:5673`), which SSE keeps fresh, so the server's strict `baseRevision` check (`server/fastify/src/commands/mutations.ts:228-231`) passes and the reset deletes every chat row (`routes/commands.ts:6014-6022`) — including messages appended after the export snapshot. Even a genuine mid-flight 409 does not durably protect: the outbox replay path retries once with the advanced cursor (`commands.ts:5540-5542`).
- Loss scenario: user has a generation streaming (or a second device sends a message) → clicks "export all chats" (file saved) → dwells on the two confirm dialogs while the new message lands durably → completes the second confirm → reset applies over the fresh revision → the appended message(s) are deleted and exist in no export.
- Unverified link: I traced conflict-retry on the replay path; the first-dispatch conflict disposition appears to be rollback (`executeServerCommand:5691-5692`), but the dominant path is no conflict at all because the cached cursor has already advanced.
- Fix direction: at dispatch time compare the per-chat message counts / last-message ids of `previousChatIds` against the export-time snapshot and abort (re-prompting to re-export) on mismatch; or capture the export snapshot after the final confirm, immediately before the optimistic apply.

### DL2-P3-F2 — 10-second blob-URL revoke may kill a slow save-as export that the reset then relies on

- Severity: low / Confidence: speculative
- Evidence: `src/ts/globalApi.svelte.ts:95-97` — `downloadFile` revokes the object URL 10 s after the anchor click; `exportAllChats` has already returned `true` at that point (`characters.ts:1060-1061`), so the reset gate is satisfied regardless of whether bytes ever reached disk.
- Loss scenario: user has "ask where to save each file" enabled, takes >10 s in the save dialog (or the download otherwise fails after hand-off: disk full, browser block); if the browser resolves the blob at save-confirm rather than at click, the download errors, yet the user — believing the export succeeded — completes both confirms and the reset destroys chats whose only copy was the failed download. The key unconfirmed link: modern Chromium/Firefox capture a Blob reference at click time, which would make the revoke harmless; I could not verify this per-browser from code.
- Fix direction: skip revocation (or lengthen it drastically) for the reset-gating export, or gate the reset on the File System Access API where available (`showSaveFilePicker` → verified `writable.close()`).
